# OMS backend database migrations

The OMS schema is managed by Alembic. The application no longer calls
`Base.metadata.create_all()` at startup and must not be used to apply schema
changes.

Run commands from `OMS/backend` with `DATABASE_URL` and `FERNET_KEY` set:

```bash
alembic upgrade head
alembic current
alembic revision --autogenerate -m "describe the schema change"
```

For an existing database, `alembic upgrade head` is safe even when the schema
predates Alembic: the baseline checks for existing tables and indexes, then
applies the drift-fixing revisions. A manually verified baseline can also be
stamped before upgrading:

```bash
alembic stamp 0001_baseline
alembic upgrade head
```

The backend container runs `alembic upgrade head` before Uvicorn starts, so a
new local or CI environment is initialized automatically. Do not run
`Base.metadata.create_all()` to apply schema changes.

Alembic imports the models, so `FERNET_KEY` is required even when generating
or applying a migration. To test the production-shaped existing-schema path,
provide a disposable PostgreSQL URL via `OMS_TEST_POSTGRES_URL` when running
`tests/test_migrations.py`.

## Production environment and Fernet key rotation

OMS production requires these environment variables:

- `FERNET_KEY`: a 32-byte urlsafe-base64 Fernet key.
- `DATABASE_URL`: the production PostgreSQL URL, kept in `OMS/.env` on the
  host and never committed or supplied by CI.
- `JWT_SECRET_KEY`: the shared JWT signing/verification secret used by
  identity-service, PMI, OMS, and WMS.
- `INTERNAL_SERVICE_TOKEN`: shared secret key (`X-API-Key`) for inter-service authentication (default: `oms_wms_internal_api_key_secret_2026`).
- `CORS_ALLOWED_ORIGINS`: the comma-separated browser origins allowed by OMS (e.g. `https://oms.topvnsport.com,http://localhost:13101,http://localhost:3000,http://127.0.0.1:13101`).
- `PIM_API_URL`: URL for PIM/PMI service integration (default: `http://pim-api:8000`).
- `WMS_API_URL`: URL for WMS service integration (default: `http://wms-api:8002`).

Generate a new Fernet key without committing it:

```bash
python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

The production deploy receives `FERNET_KEY` and `JWT_SECRET_KEY` from GitHub
Actions secrets and upserts only those keys into the existing service `.env`
files. `DATABASE_URL` must be provisioned manually in `OMS/.env` before
deployment; the deploy script does not overwrite it or any other host setting.
Missing required values fail during Compose interpolation with an explicit
message.

### One-time Fernet rotation

The old fallback key was exposed in Git history and must not remain the
production key. On a controlled maintenance run, in this order:

1. Back up the `system_configs` table.
2. Set the new `FERNET_KEY` in the host's `OMS/.env`.
3. Run `alembic upgrade head` so `system_configs.config_value` is `TEXT`.
4. Recover the old key from the pre-OMS-006 revision locally with
   `git show 3116bf3~1:OMS/backend/models.py` and pass it only as
   `FERNET_KEY_OLD`; never save it in a file.
5. From `OMS/backend`, run a dry run and then the transaction:

   ```bash
   FERNET_KEY_OLD='(old key supplied out-of-band)' \
   FERNET_KEY='(new key from OMS/.env)' \
   DATABASE_URL='(production URL supplied out-of-band)' \
   python scripts/reencrypt_system_configs.py --dry-run

   FERNET_KEY_OLD='(old key supplied out-of-band)' \
   FERNET_KEY='(new key from OMS/.env)' \
   DATABASE_URL='(production URL supplied out-of-band)' \
   python scripts/reencrypt_system_configs.py
   ```

The utility is idempotent and reports only config keys and counts. If the
table contains only Zalo settings, an alternative is to deploy the new key
and re-enter all Zalo app/token values through the admin UI; those exposed
tokens should be rotated regardless. Do not run either procedure against
production without an approved backup and maintenance window.

The deploy smoke check reads an actual `system_configs` row through the ORM
and verifies that a token generated by identity-service is accepted by OMS.
WMS uses the same JWT secret and validates JWT bearer tokens directly; it does
not sign identity tokens.
